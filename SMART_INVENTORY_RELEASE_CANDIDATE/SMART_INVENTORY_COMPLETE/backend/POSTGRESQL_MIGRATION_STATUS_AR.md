# حالة نقل SMART INVENTORY إلى PostgreSQL

## الهدف المعتمد
- PostgreSQL قاعدة البيانات المركزية متعددة المستخدمين.
- CSV صيغة تصدير ونسخ احتياطية قابلة للتنزيل، وليست قاعدة البيانات التشغيلية.
- GitHub لحفظ السورس كود وملفات ترحيل قاعدة البيانات فقط، وليس لتشغيل قاعدة البيانات الحية أو تخزين بيانات الموظفين الفعلية.
- واجهة ويب واحدة آمنة يمكن الوصول إليها من أجهزة ومواقع متعددة.

## ما أُنجز في هذه المرحلة
- إضافة مسودة مخطط PostgreSQL أولي في `migrations/001_initial_postgresql.sql`.
- إضافة هذا المستند لتحديد حدود المرحلة ومنع اعتبار المخطط وحده ترحيلاً مكتملاً.

## ما لم يُنجز بعد (مهم)
هذه المرحلة **ليست نسخة تشغيل PostgreSQL بعد**. ملف `app.py` الحالي ما زال يستخدم `sqlite3` مباشرة. لا تضف بيانات تشغيل فعلية ولا تنشر رابط استخدام عام اعتماداً على هذا الفرع.

قبل اعتماد PostgreSQL يجب تنفيذ واختبار:
1. استبدال اتصال SQLite بطبقة اتصال PostgreSQL وإدارة معاملات آمنة.
2. تعديل أوامر SQL غير المتوافقة، مثل `INSERT OR REPLACE` و`last_insert_rowid()` و`PRAGMA`، والتحقق من أنواع النتائج والتواريخ.
3. ترحيل الحسابات والجداول والبيانات التجريبية بأداة ترحيل قابلة لإعادة التشغيل.
4. إنشاء حساب المدير الأول من متغيرات بيئة آمنة، لا من ملف كلمات مرور داخل المستودع.
5. إضافة اختبارات تكامل على PostgreSQL حقيقي، واختبارات تزامن وتعارض ومزامنة Offline.
6. إضافة تصدير CSV محمي بالصلاحيات، مع UTF-8 BOM لدعم Excel العربي، وتصدير من لقطة بيانات متسقة.
7. إضافة نسخ احتياطي واستعادة موثقين، مع الاحتفاظ بنسخ خارج GitHub.
8. نشر التطبيق وقاعدة البيانات على خدمة تشغيل/استضافة، وإعداد HTTPS وإدارة الأسرار والنسخ الاحتياطية.

## تنبيه حول GitHub
لا تُحفظ قاعدة PostgreSQL الحية أو ملفات CSV التي تحتوي بيانات موظفين أو أرصدة فعلية داخل Git repository. Git يسجل تاريخ التغييرات، والملفات قد تبقى في تاريخ المستودع حتى بعد حذفها من أحدث نسخة. اجعل المستودع Private، واستخدم GitHub للسورس كود فقط. تُنزّل ملفات CSV من التطبيق إلى جهاز المدير أو إلى مخزن نسخ احتياطي خاص وآمن.

## قرار القبول
لا يُعلن الإصدار جاهزاً إلا بعد نجاح اختبارات PostgreSQL والتزامن والصلاحيات وتصدير CSV والاستعادة، ثم تجربة تشغيل فعلية على أجهزة متعددة.
